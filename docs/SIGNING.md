# 固定签名与录屏授权

macOS 按应用的签名身份要求识别已授权应用。ad-hoc 身份与具体代码哈希绑定，修改内容后可能失去已有录屏授权；仅固定安装路径不能解决这一点。

## 本地开发

`make dev` 构建并安装独立的 `/Applications/Screenshot Dev.app`（`com.kirktools.screenshot.dev`），自动生成并复用开发证书。开发证书位于主仓库 `.local/signing/`，所有 Git worktree 共用。日常 `/Applications/Screenshot.app` 不会被覆盖或停止。两个应用的设置和录屏授权独立，开发版默认快捷键为 `⌃⌥2 / ⌃⌥7`，不提供正式更新入口。私钥只在专用钥匙串中；脚本不加入系统信任、不修改录屏数据库、不自动提权，也不在后台采集。

从旧 ad-hoc 版第一次切换可能仍需授权。此后代码可以持续变化，证书身份保持一致。若 macOS 因撤销权限或系统策略要求确认，应遵循系统提示；不要承诺任何环境下永不提示。

请私下备份整个 `.local/signing/`，不要提交或公开。丢失、删除或重建证书会改变身份；脚本发现资料不完整时会停止，不会悄悄生成替代证书。更换电脑或克隆到另一目录时，需要恢复这份资料才能延续身份。

## GitHub 正式更新（不付费方案）

先运行 `make signing-prepare`，在 `.local/signing/release/` 单独准备固定发布证书，不上传。开发密钥不会用于分发。维护者之后可显式运行 `make signing-ci`，将发布专用的加密钥匙串保存到 `kirktools/screenshot` 的 Actions Secrets：

- `MACOS_SIGNING_KEYCHAIN_BASE64`：只包含该项目证书和私钥的加密专用钥匙串。
- `MACOS_SIGNING_PASSWORD`：专用钥匙串密码。

该命令需要本机现有 GitHub CLI 登录及仓库管理权限，不触发发布，不读取 Apple 账号或其他钥匙串身份。不要在不可信代码或他人的电脑上执行；能修改发布工作流的人可能使用或导出 Actions 中的密钥，须保护仓库写权限。

Release 工作流只导入固定证书，不按版本重新生成；未配置时明确失败，不发布 ad-hoc 更新包。临时 runner 完成后清理钥匙串。CI 的普通测试产物仍可用 ad-hoc，不能替代日常更新版本。

应用更新器会核对无 Apple Team ID 的当前应用与新包的证书指纹，拒绝更换证书或退回 ad-hoc；初次从旧 ad-hoc 切换仍可能需要一次授权。同一固定证书的正常更新目标是延续已有授权，仍需在真实系统上验收。

自签名没有 Apple 的分发信任，也没有公证。下载或更新后的 Gatekeeper 核验与“仍要打开”提示可能仍存在，这与录屏授权是两个不同问题。若以后采用 Developer ID + 公证，需要另行配置 Apple 凭据、可信时间戳及公证流程；切换身份应安排一次迁移验收。

## 验收

1. `make dev` 后完成首次录屏授权并截取非敏感画面。
2. 修改代码，再运行 `make dev`。确认签名身份要求相同，直接截图无需重新开关权限。
3. 用同证书签两个不同版本，在一次性测试账户验收“检查更新 → 安装 → 重启 → 截图”。检查签名、截图与 Gatekeeper 提示分别记录。
4. `make signing-test` 使用假命令及临时资料验证策略，不修改真实钥匙串。原生更新回归另外覆盖证书不一致和降级拒绝。

先构建日常版并执行 `make signing-prepare`；然后 `make signing-integration-test` 在本机临时目录模拟 runner 载入专用钥匙串，签两份内容不同的应用包，断言代码哈希不同、身份要求一致，并让 macOS 验证新版满足旧版的身份要求。它不等于真实录屏授权或 Gatekeeper 升级验收，不上传或安装应用。
